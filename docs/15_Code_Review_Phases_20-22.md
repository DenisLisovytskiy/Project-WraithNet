## 1. Correctness

### 1.1 Phase 20 — Jet frame catalog & independent heading
* `JetFrameType`/`JetFrameSpec`/`JET_FRAME_CATALOG` in `config.py` exactly match the required shape, and `STRIKE_FIGHTER`'s `max_speed=5.0`/`hp=5` are verified byte-identical to the legacy `JET_SPEED`/`JET_HP` globals both in a code comment (`# must equal JET_SPEED`) and in a dedicated test (`test_default_scenario_jets_match_historical_speed_and_hp`).
* `config.JET_SPEED`/`config.JET_HP` were **not** deleted (the doc allowed keeping them if something outside `world.py` still reads them directly) — confirmed they're still read by `viewer/render.py`'s HP bar, per `config.py`'s own comment, and by tests. `world.py` itself reads exclusively from `JET_FRAME_CATALOG`, confirmed via `grep -rn "config.JET_SPEED\|config.JET_HP" wraithnet/world.py` → zero matches (Phase 20 acceptance criterion #4, verified directly).
* `fuel_capacity`/`fuel_burn_per_tick` values are not arbitrary placeholders — `config.py`'s comment derives them from a concrete "endurance in ticks × max_speed ≈ distance range vs. `GRID_WIDTH`" argument for each of the three frames, and explicitly justifies `STRIKE_FIGHTER`'s 80-tick capacity as "~2.5× the 32-tick PoC so Phase 22 bingo-fuel has headroom" — which turned out to be exactly right (see §1.3/§3).
* Heading convention (`0° = facing +y`, clockwise) is documented once, precisely, in `JetAgent.heading`'s comment and in the new `wraithnet/geometry.py` module docstring, and consistently reused everywhere the convention matters (`_apply_heading_rotation`, `_target_in_firing_arc`, `agents.py::decide_intent`) via the shared helpers — see §1.4.
* `_apply_heading_rotation`'s shortest-signed-angle logic is delegated to `wraithnet.geometry.shortest_signed_angle` rather than reimplemented inline, and is proven correct in both directions with the exact test cases the doc asked for: a same-tick snap when within `turn_rate_deg_per_tick`, a clockwise-shorter 70° turn, and a counter-clockwise-shorter turn through 0° (`10° → 350°`, correctly rotating backward to `358°`, not forward through `180°`).
* Rotation is applied **before** `MOVE`/`STRIKE` dispatch each tick, exactly the ordering Phase 21 needed (a jet that finishes turning this tick can fire the same tick) — the ordering decision is documented in-line in `step()`'s comment rather than left implicit, and Phase 21's own rotate-then-strike acceptance test (`test_narrow_arc_weapon_rotates_into_arc_before_first_strike`) empirically depends on and confirms this.
* `ActionIntent.desired_heading`/`Observation.current_heading` added exactly as specified, with no speculative heading-setting logic added to `agents.py` in this phase (verified by reading `agents.py`'s state at this phase boundary — `decide_intent` didn't yet set `desired_heading` until Phase 21's changes, which is correctly a *separate* concern reviewed in §1.2).

### 1.2 Phase 21 — Weapon catalog: range, firing arc, slot cost, new weapons
* `WeaponSpec`/`WEAPON_CATALOG` replace the old flat `STRIKE_RANGE`/`WEAPON_SUITABILITY` globals completely — confirmed via a case-sensitive `grep -rn "STRIKE_RANGE|WEAPON_SUITABILITY" wraithnet/ tests/`, which returns **zero matches** (the only look-alike hits are for the unrelated, pre-existing `TraceHeader.strike_range` field name, which a case-insensitive grep conflates but a case-sensitive one correctly does not).
* `JDAM`/`AIM9X` keep `range=1.0`, `firing_arc_deg=360.0`, and their exact Phase 6 suitability numbers — verified both by reading `config.py` and by `test_jdam_and_aim9x_preserve_legacy_range_arc_and_suitability`'s exact-equality assertions.
* The two new weapons are well-designed, not throwaway filler:
  * `AMRAAM` (range 20, all-aspect) is deliberately placed *outside* `SAM_ENGAGEMENT_RANGE` (15), so a jet can kill a SAM site without ever entering its engagement envelope — a genuine tactical reason to prefer it, not just a "bigger JDAM." Its `HARDENED_BUNKER` suitability (0.3) is deliberately mediocre so `JDAM` remains the rational bunker weapon, avoiding the "strictly-better AIM9X" trap the doc explicitly warned against. Verified by `test_amraam_is_longer_range_all_aspect_and_not_a_strict_aim9x_upgrade` and directly demonstrated hitting a target 180° behind the jet's heading (`test_amraam_strikes_a_target_behind_the_jet`).
  * `GUN_POD` (range 0.5, 60° cone, `damage_per_hit=2`) is shorter-range than `JDAM` but does double damage, which is the concrete, config-comment-documented reason a rational agent would ever accept the extra maneuvering cost of turning to bear it. Verified by `test_gun_pod_is_shorter_range_narrow_forward_cone`.
* `_apply_strike`'s new firing-arc gate and `agents.py::decide_intent`'s "rotate to bear" prediction both delegate to the **same** shared function, `wraithnet.geometry.is_in_firing_arc` — this is a stronger, more drift-proof implementation than the phase doc's own suggestion (which only asked for "a shared helper or a cross-checking test... do not duplicate with any drift"). Using one function instead of two independently-written-but-tested-equal functions eliminates the drift risk structurally rather than just detecting it after the fact.
* The cross-check test the doc specifically called for (`test_agents_and_world_agree_on_firing_arc_gate`) still exists and is genuinely meaningful even with a shared helper: it exercises `model._target_in_firing_arc` (which wraps the shared helper) against six hand-computed cases including both exact-edge (30° off a 60° cone) and just-outside (31° off) boundaries, and confirms `_apply_strike`'s actual damage/payload outcome matches the geometric prediction in every case.
* `decide_intent`'s three-way branch (`STRIKE` when in range and in arc; `IDLE` with `desired_heading` set when in range but not yet in arc — explicitly not consuming payload or losing the contract; `MOVE` with `desired_heading` **also** set while still closing distance) is implemented exactly as specified, including the "turn while closing" improvement the doc called out as easy to accidentally skip. All three branches have dedicated tests, and `test_narrow_arc_weapon_rotates_into_arc_before_first_strike` proves the full multi-tick rotate-then-strike behavior end-to-end (not immediately, not never — exactly Phase 21's acceptance criterion #3).
* `ScenarioConfig`'s ordnance-slot-capacity validator matches the doc's exact error-message shape (`"Jet 'Jet_2' payload requires 8 ordnance slots but its STRIKE_FIGHTER frame only has 7"`), reuses `WEAPON_CATALOG`/`JET_FRAME_CATALOG` rather than hardcoding numbers, and is verified against both the default scenario (fits, confirmed by `test_default_scenario_payloads_fit_strike_fighter_ordnance_slots`) and a deliberately-overflowing hand-crafted one (`test_rejects_payload_exceeding_ordnance_slots`).

### 1.3 Phase 22 — Fuel consumption & bingo-fuel RTB
* `RTB_FUEL_SAFETY_MARGIN`/`RTB_LANDING_RADIUS` and `DEFAULT_HOME_BASE` are all present with the one-line rationale comments this codebase's convention requires (matching `config.SCENARIO`'s existing `hp_required=5` comment style). `DEFAULT_HOME_BASE=(2.0, 2.0)` is justified geometrically in the comment (SW corner, away from both targets/SAM/jammer, not on a jet spawn) — checked against `config.SCENARIO`'s actual coordinates and it holds up.
* `home_base` was added to `ScenarioConfig` with the same in-bounds validation as every other position field (folded into the existing `_entity_positions` helper rather than a bespoke check), and `scenarios/default.json` was updated with the matching value — verified via `test_default_scenario_home_base_is_sw_corner` and `test_rejects_home_base_outside_grid`.
* Fuel state/burn/landing/reap ordering in `WraithNetModel.step()` matches Part C's pseudocode exactly, including the one subtlety that's easy to get backward: **landing is checked before the fuel-exhaustion reap**, so a jet arriving home with exactly `0.0` fuel left is recorded as a safe landing, not a loss. This exact boundary is independently tested twice — once proving the "just outside the radius" jet is *not* landed (`test_rtb_jet_lands_inside_radius_not_just_outside`) and once proving the "0 fuel exactly at the pad" case is landed, not reaped (`test_arriving_home_on_empty_tank_is_a_landing_not_a_loss`).
* Fuel exhaustion is a genuinely independent condition from `hp` — confirmed by reading the reap predicate (`jet.is_destroyed or jet.fuel <= 0`, never `jet.hp = 0`) and by the case-sensitive acceptance grep (`grep -rn "jet.hp = 0" wraithnet/world.py` → zero matches), plus a test that explicitly asserts `hp_before > 0` survives a fuel-exhaustion reap (`test_fuel_exhaustion_reaps_without_counting_as_landed`).
* `JetAgentRuntime.begin_rtb()`/`bingo_fuel_reached()` match the spec, with one small, correct hardening beyond the doc's literal pseudocode: `begin_rtb` aborts open management if `role == "MANAGER"` **or** `managed_target_id is not None` (the doc only checked the role), which is a strictly safer condition and costs nothing. Idempotency (`begin_rtb()` called twice is a no-op the second time) is explicitly tested.
* The `role` audit the doc demanded ("audit every place in `agents.py` that branches on `self.role`, do not assume the existing gates are sufficient without verifying each one explicitly") was genuinely done, not just asserted: `scan_and_negotiate`, `_maybe_bid`, and `try_become_manager` all gate on `role != "IDLE"`/`role == "IDLE"`, so `"RTB"` is excluded for free everywhere, and this is proven — not just reasoned about — by `test_rtb_jet_never_bids_on_cfp_or_becomes_manager`, a real async integration test that sends a live `CFP` broadcast at an `"RTB"` agent and asserts no `BID` is ever produced.
* `bridge.py`'s Part F wiring (`began_rtb_this_tick`, syncing `model.jets[agent_id].is_rtb = True`, folding both destroyed and newly-RTBing IDs into the same `_notify_managers_of_losses` call) matches the doc's exact snippet, including the "do not otherwise modify `_notify_managers_of_losses`'s body" constraint (confirmed unchanged by reading it). The claim that landed/fuel-exhausted jets are *already* handled correctly by the existing `destroyed_this_tick = alive_before - set(self.model.jets)` computation — which the doc explicitly said needed empirical proof, not just trust — is backed by two dedicated integration tests (`test_landed_jet_runtime_is_removed_from_bridge_agents`, `test_fuel_exhausted_en_route_runtime_is_removed_not_landed`), both of which assert on `bridge.agents` membership after a real tick, not just `model.jets`.
* Manager-fallback-on-RTB itself is proven with a full integration test (`test_rtb_contractor_notifies_manager_like_a_combat_loss`) that runs a real bridge for several ticks, forces a specific contractor's fuel down to just above its bingo threshold (with the exact arithmetic justified in a comment: `(10,10)→(2,2) ≈ 11.3 units, bingo ≈ 2.7 for STRIKE_FIGHTER, fuel=2.0 triggers without landing this tick`), and asserts the manager's `managed_contracts` no longer lists that jet afterward.

### 1.4 `wraithnet/geometry.py` — a good, unprompted improvement
Phase 21's doc suggested (but didn't require) factoring `_bearing_to`/`_angular_distance` into a shared module to prevent drift between `agents.py` and `world.py`. The implementation went further and did this properly: a new, dependency-free `wraithnet/geometry.py` module holds `bearing_to`, `shortest_signed_angle`, `angular_distance`, and `is_in_firing_arc`, with the heading convention documented once at the top of the file and referenced from both `world.py` and `agents.py` rather than restated. This is a clean, low-risk refactor that directly serves the design's own stated risk (never let arc-checking logic exist in two places), and both call sites were confirmed to actually import from it rather than keeping a parallel copy.
