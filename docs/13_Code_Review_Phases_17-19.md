# Code Review — Phases 17–19 (Camera Modes/HUD/Mission Brief, Scenario Editor, Editor→Launch Integration)

**Scope reviewed:** `viewer3d/cameras.py`, `viewer3d/hud.py`, `viewer3d/highlights.py`, `viewer3d/editor.py`, `viewer3d/launch.py`, and the corresponding changes to `viewer3d/app.py` / `viewer3d/scene.py`, plus `tests/test_viewer3d_highlights.py`, `tests/test_viewer3d_editor.py`, `tests/test_viewer3d_launch.py`, and the `tests/test_viewer3d_smoke.py` additions.

**Verdict: pass.** This is the strongest of the implementation batches reviewed so far — it follows the phase docs closely, makes every deliberate deviation an explicit, documented decision rather than a silent shortcut, and the test suite genuinely proves the headline end-to-end promise ("customize → preview → launch → watch it live, in one window") rather than just exercising units in isolation. No `wraithnet/` changes, no new `viewer3d`↔`viewer` coupling, no scope creep. Two minor test gaps and one informational note are flagged below; nothing here blocks moving on to Phases 20–26.

## 1. Correctness

### 1.1 `viewer3d/cameras.py` (Phase 17, Part A)
* `OrbitCamera`, `ChaseCamera`, `MissionBriefCamera` all match the sketched public surface (`__init__` + `update(dt, ...)`) exactly, so `app.py`'s per-frame dispatch (`_update_camera`) can swap between them uniformly.
* `_camera_node(base)` correctly handles the `window-type none` headless case (Phase 16's established quirk) by falling back to a dummy `NodePath` stored on `base._viewer3d_dummy_camera`, so `set_pos`/`look_at` calls are always safe to make and testable without a real window. This is the same defensive pattern Phase 16 used for `ShowBase.camera`.
* Jet selection for chase mode uses `Tab`/`N` cycling over `header.jet_ids` rather than 3D mouse-picking — explicitly the phase doc's sanctioned fallback ("pick whichever you can make robust and document the choice"), and it's documented in the module docstring and `app.py::_cycle_selected_jet`'s comment. Correct call: 3D picking under `window-type none` would be unreliable to test headlessly anyway.
* `ChaseCamera`'s heading convention (`atan2(dx, dy)`, degrees from +y) is documented as matching `scene.py`'s billboard yaw convention, and is verified in practice by `viewer3d/scene.py::update_tick` computing heading the same way. Consistent.

### 1.2 `viewer3d/hud.py` (Phase 17, Part B)
* Four independently-positioned corner panels (top-left mission info, top-right force status + role swatches, bottom-right coordinates + minimap, bottom-left controls), matching the "not one dense sidebar" requirement and the Ace Combat bracket-panel reference.
* `DisconnectedEvent`/`EndEvent` surfacing, which Phase 16 deliberately left a silent no-op, is now genuinely surfaced: `_update_mission_info` renders `disconnect_reason` into the `[ STATUS ]` line, and a distinct `"launch_failed"` status (anticipating Phase 19) is handled too.
* Minimap: implemented as a hand-drawn `DirectFrame` dot-plot (option (b) from the phase doc) rather than a second orthographic viewport (option (a), the "preferred" choice). The module docstring gives a concrete, correct justification: `window-type none` leaves `ShowBase.win` as `None`, so a second `DisplayRegion` isn't reliably available in the same headless test configuration the whole test suite depends on. Given the project's hard requirement of headless-testable Panda3D (established since Phase 16), this is the right trade-off, not a shortcut — a second real viewport would have made the minimap effectively untestable.
* `update()`'s signature grew two optional keyword arguments beyond the phase doc's sketch (`ticks`, `orbit_center`) to support the end-of-run summary computation and the orbit-mode "where is the camera looking" coordinate line. Reasonable — the doc's code block was illustrative pseudocode, not a frozen contract, and the extra parameters are both optional with sensible defaults.
* End-of-run summary reuses `viewer3d/highlights.py::compute_run_summary` (see §1.3) rather than recomputing headline numbers inline, and reuses `viewer/render.py::ROLE_RING_COLOR`'s palette by copying the dict (not importing it), consistent with the project's standing rule that `viewer3d` must not depend on `viewer`/Pygame.

### 1.5 `viewer3d/editor.py` (Phase 18)
* `OrthoEditorCamera.screen_to_world` is a straightforward, correctly-derived affine inverse of the orthographic projection (`center ± mouse_axis * film_size/2`), and `tests/test_viewer3d_editor.py::test_screen_to_world_corners_and_center` verifies all four corners and the center against hand-computed expectations, per the phase doc's explicit ask.
* The draft is correctly kept as plain nested dicts/lists (`scenario_draft`), never a live `ScenarioConfig`, exactly per Part A's guidance — `ScenarioConfig` is only constructed transiently inside `_construct_config()`, called from `save()`/`preview()`/after edits (for live banner feedback), never held as persistent state. This is the right way to avoid fighting Pydantic on every keystroke, as the doc anticipated.
* **Validation is not duplicated.** `_construct_config` does nothing but call `ScenarioConfig.model_validate(data)` and translate `pydantic.ValidationError` via `_humanize_validation_error`; no hand-rolled `hp_required` comparisons or `len(jets) == 0` checks exist anywhere in the file. The phase doc's own suggested acceptance grep (`hp_required\s*[<>=]|len(.*jets.*)\s*==\s*0`) does surface two lines, but both are false positives of the regex's own imprecision — they're `target_hp_required={...}` dict-literal *construction* for `TraceHeader`/the draft header (i.e., `target_hp_required=` triggers the `hp_required\s*[<>=]` pattern because `=` immediately follows the differently-named field `target_hp_required`), not a re-implementation of the `hp_required >= 1` validation rule. Manually confirmed no actual duplicated validation logic exists. Worth noting for whoever runs this grep literally in the future — it will need eyeballing, not a pure pass/fail read.
* `scenario_to_header` correctly sources `sensor_radius`/`jam_radius`/`sam_engagement_range`/`strike_range` from `wraithnet.config` rather than expanding `ScenarioConfig`'s schema, exactly as Part C flagged as the right call. Field-by-field parity with `wraithnet.trace_builders`'s shared header builder (SAM sites merged into `target_*` maps) is correct and covered by `test_scenario_to_header_matches_config_constants_and_entities`.
* `preview()` reuses Phase 17's mission-brief mode via `self.base.enter_preview(header)` rather than reimplementing any camera/scene logic — confirmed by reading `app.py::enter_preview`, which does nothing but call the existing `build_static_scene` and swap `view_mode`/`camera_mode`. Matches Part C's "reuses, does not reimplement" requirement.
* `save()`/`load()`/`delete_entity()` all behave as specified: `save()` returns `None` and writes on success, a non-`None` error list and **no file write** on failure (verified by `test_save_without_jets_returns_errors_and_does_not_write` asserting `not dest.exists()`); `load()` fully replaces the draft and rebuilds the scene (verified against both draft state and the underlying `SceneHandles` node positions in `test_load_replaces_draft_and_scene`).

### 1.6 `viewer3d/launch.py` + `app.py` launch wiring (Phase 19)
* `launch_scenario` fixes the phase doc's own placeholder bug (`port_as_str_if_needed`) by using a real ephemeral-port strategy (`socket.socket().bind((host, 0))` → `getsockname()[1]`), exactly the "recommended" option the doc called out, and documents the choice in the module docstring. Verified working end-to-end by `test_sequential_launches_get_distinct_ports`.
* Goes beyond the doc's minimal sketch in ways that materially improve robustness, all well-justified:
  * A background thread drains the child's `stderr` continuously into `_stderr_lines` rather than reading it synchronously, avoiding a classic pipe-deadlock risk (a child that fills its stderr buffer while a blocking parent hasn't read from it yet) — a genuine correctness improvement over the doc's simpler illustration.
  * Each launch gets its own temp `cwd` (`tempfile.mkdtemp`) so concurrent runs don't fight over `results/trace.jsonl`, plus a `PYTHONPATH` injection so `python -m wraithnet.main` still resolves from a temp cwd, plus `CREATE_NO_WINDOW` on Windows to avoid a flashing console per launch. None of this is required by the phase doc, but none of it contradicts it either, and it's exactly the kind of detail a real cross-platform "launch a subprocess from a GUI" feature needs.
  * `SimLaunchHandle.terminate()` escalates from `terminate()` to `kill()` after a 5s grace period — more robust than the doc's one-line `process.terminate()`.
* `app.py::on_launch_clicked` sequencing matches Part B precisely: save → (if valid) preview immediately without waiting on the subprocess → spawn → attach a fresh `StreamClient`. The one deviation — calling `_stop_sim()` first if a previous sim is still running — is exactly the documented "terminate-and-replace" resolution to Phase 19's own explicitly-left-open non-goal ("pick one behavior and document it clearly").
* Part C (slow/failed subprocess) is implemented as `_poll_sim_health`, polled every frame from the same task that drains the stream queue. It correctly distinguishes "still starting" (do nothing, let `StreamClient`'s bounded retry loop keep trying) from "crashed" (non-zero exit with no tick yet received → `view_mode = "launch_failed"`, HUD shows `handle.stderr_tail()`) from "exited cleanly" (return code 0 is treated as benign and left alone, which is correct for `wraithnet.main`'s actual behavior — it never exits 0 without having produced a full run's worth of ticks first). A "Cancel launch"/"Back to editor" control (`cancel_launch()`, wired to `Esc` and to a `_back_btn` shown on launch failure) terminates the subprocess and returns to editor mode, satisfying Part C's last requirement.
* Part D (clean shutdown) is wired through three separate paths — `on_window_close`, `userExit` (override), and `destroy` (override) — all routing through the same `_stop_sim()`, so however the window actually closes in practice (explicit `Esc`→`userExit`, or a direct `destroy()` call from a test/host), a live sim subprocess gets terminated. This is more defensive than the doc's single sketched hook and is a sensible response to Panda3D's own note that a real window-close signal isn't reliably hookable under `window-type none`.
* Isolation acceptance criterion (`grep -rn "panda3d\|viewer3d" wraithnet/ requirements.txt requirements-dev.txt requirements-viz.txt`) returns **zero matches**, confirmed by running it. `wraithnet/` remains completely unaware `viewer3d` exists, even after full end-to-end integration.
