## 1. Phase 14 — Scenario Schema, IO & Config-Driven World

* **`wraithnet/scenario_schema.py` implements exactly the five required validations**, each with a specific, human-readable message: zero jets, duplicate ID across *any* two entity lists (not just within one list — correctly checked via a single `seen: dict[str, str]` scan over `_entity_ids()`, which pools jets/targets/sam_sites/jammers together), position outside `[0, grid_width] × [0, grid_height]`, `hp_required < 1` (targets and SAM sites both), and negative payload counts. All five have dedicated tests in `tests/test_scenario_schema.py`, matching the phase doc's explicit list.
* **`_default_scenario()` is a thin wrapper around `config.SCENARIO`** (`ScenarioConfig.model_validate(config.SCENARIO)`), exactly the pattern the phase doc sanctioned as the simpler of its two allowed options — `config.SCENARIO` remains the single literal source of truth, confirmed by `test_scenario_config_accepts_builtin_poc_scenario` asserting equality between the two construction paths.
* **`wraithnet/world.py`'s spawn loop is fully scenario-object-driven**: `WraithNetModel.__init__` takes `scenario: ScenarioConfig | None`, defaults via `_default_scenario()`, and `_spawn_scenario()` reads attribute access (`t.target_id`, `j.position`, etc.) throughout — no leftover dict-subscript access against a spec object anywhere.
* **Acceptance criterion #5 verified directly**: `grep -rn "config.SCENARIO\[" wraithnet/world.py` returns zero matches (in fact zero matches for `config.SCENARIO` at all in `world.py` — the module doesn't even import `config.SCENARIO` anymore, only the `config` module for constants like `JET_HP`).
* **Grid size is genuinely scenario-driven, not hardcoded**: `mesa.space.ContinuousSpace(self._scenario.grid_width, self._scenario.grid_height, ...)` reads from the scenario, and `tests/test_world.py::test_model_uses_scenario_grid_size_not_config_constants` confirms `model.space.x_max`/`y_max` reflect a custom grid size, not `config.GRID_WIDTH`/`GRID_HEIGHT`.
* **`wraithnet/bridge.py`/`wraithnet/main.py` wiring matches the doc**: `WraithNetBridge.__init__` forwards `scenario` straight to `WraithNetModel`; `main.py` adds the `--scenario PATH` flag via stdlib `argparse` and calls `load_scenario()` only when the flag is present, otherwise passing `None` through unchanged.
* **`scenarios/default.json` exists, is committed, and round-trips exactly**: `tests/test_scenario_io.py::test_load_committed_default_json_matches_builtin_scenario` confirms `load_scenario(scenarios/default.json).model_dump() == _default_scenario().model_dump()`. Manually inspected the file's contents — they match `config.SCENARIO` field-for-field (including `Target_A.hp_required = 5`, the deliberately-cooperation-forcing value from Phase 0's design review).
* **Backward compatibility is airtight**: every pre-Phase-14 test that constructs `WraithNetModel()`/`WraithNetBridge()` with no scenario argument still passes unmodified, and `test_bare_model_still_spawns_the_builtin_poc_scenario` / `test_model_spawns_exact_scenario` in `tests/test_world.py` directly assert this is byte-for-byte identical to pre-Phase-14 behavior.
* **CLI-level regression check**: `tests/test_main.py::test_main_with_default_json_matches_main_with_no_flags` asserts `python -m wraithnet.main` and `python -m wraithnet.main --scenario scenarios/default.json` produce identical stdout — satisfies acceptance criterion #3 directly, and I re-ran both by hand to confirm.
* **A genuinely custom scenario runs end-to-end**: `tests/test_bridge.py::test_bridge_runs_custom_scenario_to_completion` and `tests/test_main.py::test_main_runs_a_custom_scenario_file` both construct a different (smaller) scenario and confirm it solves, satisfying acceptance criterion #4.

No issues found in Phase 14.

## 2. Phase 15 — Live Tick Streaming Protocol

* **The shared-builder refactor was done correctly and exactly as instructed**: the phase doc explicitly asked for option (a) — extracting `build_trace_header`/`build_trace_tick` into a shared module rather than duplicating field-mapping logic — and that's exactly what `wraithnet/trace_builders.py` does. Both `TraceRecorder` and `LiveStreamServer` now call the identical two functions; there is no second copy of the header/tick construction logic anywhere. `tests/test_live_stream.py::test_recorder_and_live_stream_emit_identical_header_and_ticks` directly proves this by running the same scenario through both sinks and asserting the parsed Pydantic objects are equal, not just similarly-shaped.
* **Backfill-on-connect is correctly implemented as synchronous-before-any-await**, and the implementation goes further than the phase doc's own sketch by explaining *why* it's race-free in a comment: `_handle_client` snapshots `self._backlog`, writes every line, and appends the writer to `self._writers` — all before the first `await writer.drain()` — so a concurrent `_send()` call (which is a plain synchronous method, only ever invoked from the same event-loop thread) cannot interleave a message between the snapshot and the subscribe. This is exactly the guarantee the design doc's §5 backfill requirement needs, and it's verified empirically, not just architecturally: `test_late_client_receives_full_backlog_without_further_ticks` and `test_multi_client_fan_out_sees_identical_complete_sequence` both pass, the latter with a genuinely early client and a genuinely late client (attached mid-run) asserted to see byte-identical complete sequences.
* **`LiveStreamServer.port` handles the ephemeral-port case** (`port=0`) by reading the OS-assigned port back from the bound socket once `start()` has run — a detail the phase doc flagged as something to "check if supported" rather than mandating a specific implementation; confirmed working via every `port=0`-based test in `tests/test_live_stream.py` and `tests/test_viewer3d_stream_client.py`.
* **The `recorder=` → `sinks=` breaking rename is complete everywhere**: acceptance criterion #5's grep (`grep -rn "recorder=" wraithnet/ tests/`) returns zero matches when re-run today. `wraithnet/main.py`, `tests/test_recorder.py`, `tests/test_bridge.py`, and every other prior call site were all updated to `sinks=[...]`.
* **`close()` is more careful than the phase doc's own sketch**: it sends the `end` message, then `await`s `drain()` on each writer before closing (catching exceptions per-writer so one bad connection can't block the others), then `wait_closed()`s each writer, then closes and waits on the server itself, and is idempotent (`self._closed` guard). `test_close_sends_end_message_to_connected_client` confirms the client-visible behavior; the extra robustness beyond the minimum needed to pass that test is a sensible defensive improvement, not scope creep.
* **Zero-effect-on-simulation claim is tested for every sink combination**, not just the two the phase doc listed individually: `test_sinks_have_zero_effect_on_summarize` checks `sinks=[]`, `[recorder]`, `[live_server]`, and `[both]` all produce an identical `summarize()` result from the same scenario — a strictly stronger test than the doc's minimum bar.
* **No new dependency**: `live_stream.py`/`trace_sink.py`/`trace_builders.py` use only `asyncio`, `json`, and stdlib typing — confirmed by inspection, satisfying acceptance criterion #1.
* **`wraithnet/main.py`'s `--live`/`--live-host`/`--live-port` flags match the doc's sketch exactly**, including the "always write the file, `--live` only adds the socket" guarantee — `tests/test_main.py::test_main_live_completes_without_a_client` confirms a live run with zero connected clients still completes and prints the normal summary, and I independently reproduced this by hand (`--live --live-port 0` → "Live stream listening on 127.0.0.1:58294" followed by the identical normal summary).

No issues found in Phase 15.

## 3. Phase 16 — Panda3D Viewer Skeleton: Static Scene & Live Stream Client

* **`requirements-3d.txt` correctly documents why no CE-fork-style workaround was needed** (unlike `requirements-viz.txt`'s `pygame-ce` substitution): the comment claims Panda3D 1.10.16 ships official cp314 Windows wheels, and this was independently confirmed in this environment (`pip show panda3d` → `Version: 1.10.16`, `import panda3d` succeeds).
* **`viewer3d/stream_client.py` is genuinely Panda3D-free**, satisfying acceptance criterion #3 directly: `grep -rn "import panda3d\|from panda3d\|from direct" viewer3d/stream_client.py` returns zero matches, and `viewer3d/__init__.py` is a docstring-only module with no eager imports of `scene`/`app`, so `from viewer3d.stream_client import ...` alone never pulls in Panda3D. `tests/test_viewer3d_stream_client.py` exercises the real connect-retry, exhausted-retry, and header/tick-in-order paths against a real `LiveStreamServer`, matching the phase doc's three required test cases exactly.
* **Acceptance criterion #4 verified directly**: `grep -rn "panda3d" wraithnet/ requirements.txt requirements-dev.txt requirements-viz.txt` returns zero matches — the core simulation package and both prior requirements files remain completely unaware `viewer3d/` exists.
* **`viewer3d/scene.py` follows the design doc's revised billboard-glyph style**, not the phase doc's own literal "solid 3D primitives" placeholder text — this is a correct and appropriately-flagged deviation, since the phase doc itself deferred to `docs/09_..._Design_Document.md §6.3`'s "camera-facing billboards, not solid 3D primitives" requirement, which supersedes the placeholder pseudocode. Vertex-colored `Geom` polygons parented under `set_billboard_point_eye()` nodes were chosen over `CardMaker` + texture, which the phase doc explicitly allowed as "an acceptable simplification for this phase" (flat-colored geometric quads/triangles, no texture) — documented in the module's own docstring.
* **Coordinate mapping and altitude handling match the design doc exactly**: sim `(x, y)` maps directly to Panda3D `(x, y)`; `JET_ALTITUDE = 8.0` is presentation-only with a small per-jet index-based vertical offset (`0.35 * idx`) to avoid perfectly overlapping jets at the same position, which is exactly the pattern the phase doc suggested for this exact problem.
* **`build_static_scene`'s jet-placement-before-first-tick behavior matches the doc's explicit guidance**: jets are placed at the grid center and hidden (`anchor.hide()`) until the first `TraceTick` arrives, rather than blocking scene construction on having tick data — confirmed both by reading the code and by `test_build_static_scene_and_update_tick_destroyed_target_and_removed_jet` asserting `handles.jets["Jet_1"].is_hidden()` immediately after `build_static_scene`, then `not handles.jets["Jet_1"].is_hidden()` after the first `update_tick`.
* **`update_tick`'s destroyed-target and removed-jet semantics are exactly analogous to `viewer/render.py`'s Phase 12/13 rules**, as instructed: a destroyed target gets a grey wireframe render mode (not a texture swap) and its SAM ring hidden; a jet absent from `tick.jets` is fully removed from the scene graph (`remove_node()`) with no tombstone left behind, matching Phase 11's `TraceTick` semantics of simply omitting destroyed jets. Both are directly tested, not just asserted by inspection.
* **Jet orientation uses the doc's explicitly-sanctioned placeholder heuristic**: in-plane roll derived from the displacement between the previous and current tick's position (`atan2(dx, dy)`), defaulting to facing "north" (+y) on the very first tick — exactly what the phase doc asked for, and exactly the kind of placeholder that Phase 20's real `heading` field will later replace (tracked correctly in `docs/phases/Phase_24_...md`'s plan, not a surprise regression to fix now).
* **`viewer3d/app.py`'s `WraithNetViewer3D` matches the phase doc's skeleton almost verbatim**, with one small, sensible robustness addition beyond the doc's sketch: `if self.win is not None` / `if self.camera is not None` guards around background-color and camera setup, which the doc's own sketch didn't have but which are necessary for the `window-type none` headless test mode (`ShowBase.camera` is `None` in that mode) — confirmed this is exactly why `tests/test_viewer3d_smoke.py`'s own comment calls this out, and the guards are what make that smoke test possible at all without a real display.
* **The headless Panda3D test config was correctly identified and documented**: `loadPrcFileData("", "window-type none")` (plus `audio-library-name null` and `notify-level error` to quiet warnings), confirmed via a comment in `tests/test_viewer3d_smoke.py` stating this was verified working on the installed Panda3D 1.10.16 / Windows combination — and independently reconfirmed here by actually running the full suite, where this test passed for real (not skipped) rather than merely being present in the file.
* **The full live-stream-to-3D-scene pipeline was independently verified end-to-end**, not just unit-by-unit: `test_viewer_app_drains_live_stream_without_raising` spins up a real `WraithNetBridge` + `LiveStreamServer` on a background thread, points a real `WraithNetViewer3D` at it, steps the Panda3D task manager in a loop, and asserts the header arrives, the scene builds, and `"Solo_Jet"` ends up in `app._handles.jets` — this is the closest available headless proxy for acceptance criterion #2's "manual visual confirmation," and it passes.

No issues found in Phase 16. (Acceptance criterion #2 itself — a human watching a real window update live — still requires an actual display, which isn't available in this environment; the headless smoke test above is the closest verifiable proxy, exactly as the phase doc anticipated when it wrote "if not, rely on the headless smoke test... and note in your final summary that manual visual confirmation is still recommended." Consider doing that one manual check yourself: `python -m wraithnet.main --live` in one terminal, `python -m viewer3d.app 127.0.0.1 8765` in another.)

## 5. Minor observations (no action required for Phases 14–16)

* **Out-of-scope, uncommitted change spotted in passing**: `git status` shows `viewer/render.py`, `tests/test_viewer_render.py`, and `tests/test_viewer_smoke.py` (all Phase 12/13 2D-viewer files, untouched by Phases 14–16) currently have uncommitted local modifications — most notably, `_font()`'s small `_font_cache` dict was removed in favor of creating a fresh `pygame.font.Font` per call. This is plausibly a fix for a real cross-test-session issue (a module-level font cache surviving across separate `pygame.init()`/`pygame.font.quit()` cycles in different test functions can hold a stale/invalidated `Font` handle), but it wasn't possible to verify against a live Pygame install in this environment (Pygame isn't currently installed here — see the one skipped test above), and it's unrelated to this review's Phase 14–16 scope. Worth a quick sanity check (`pip install -r requirements-viz.txt && pytest tests/test_viewer_smoke.py -v`) before committing it, but it does not block or affect Phases 14–16 in any way.
* **`viewer3d/scene.py`'s `update_tick` re-finds child nodes by wildcard path** (`anchor.find("**/glyph-*")`, `anchor.find("**/sam-ring-*")`) every tick rather than caching a direct `NodePath` handle in `SceneHandles`. At this project's entity counts (a handful of jets/targets/SAM sites), this has no measurable performance impact and is not a bug, just a minor style note — if Phase 17+ ever needs per-frame updates at a much larger scale, caching these lookups in `SceneHandles` would be the natural next step.
